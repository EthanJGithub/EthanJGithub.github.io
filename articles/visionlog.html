VisionLog: real-time object detection that runs entirely in your browser

June 2026·9 min read·VisionLog
Open live demo ↗View code ↗

VisionLog is a real-time object-detection web app where the visitor uploads a video file or turns on their webcam, the model draws boxes and labels live, and every detection is logged to a database you can then query in plain English. The twist: the entire detection pipeline runs client-side, in the browser, on the visitor's own GPU. There is no inference server, no GPU bill, and no cold start.

Why run inference in the browser?

The usual architecture for a CV demo is: upload frames to a server, run the model on a rented GPU, send results back. That is expensive to keep online, it cold-starts, and it falls over the moment more than one person opens your demo. For a portfolio piece that recruiters click at random, none of that is acceptable.

So VisionLog pushes the model to the edge — literally the visitor's machine. It uses onnxruntime-web with the WebGPU execution provider, falling back to WASM/CPU when WebGPU isn't available. The model weights are static assets served from the CDN; the first load pulls the ONNX file once and caches it.

The model: YOLO26, NMS-free

VisionLog ships YOLO26 in n/s/m/x sizes plus an open-vocabulary variant. YOLO26 exports an end-to-end, NMS-free graph — the output tensor is already (1, 300, 6) (300 candidate detections, each [x1, y1, x2, y2, score, class]), so there is no non-max-suppression to run in JavaScript for the main models. I exported at a static 640×640 input at opset 12; a dynamic-shape export was actually slower in onnxruntime-web, so static won.

Because inference runs on the visitor's own GPU, frame rate depends entirely on their hardware — so quoting my machine's numbers wouldn't tell you much. In practice the smaller models (n/s) are comfortably real-time capable on a typical modern GPU, while the larger models trade speed for accuracy. The largest model (x, 223 MB) exceeds GitHub's 100 MB file limit, so it's served only on the deployed CDN and the UI gracefully marks it unavailable if the asset is missing.

Open-vocabulary detection without a 570 MB CLIP encoder

"Open vocabulary" usually means pairing a detector with a CLIP text encoder so you can type arbitrary class names. That encoder is ~570 MB — a non-starter for a client-side app. Instead, VisionLog bakes a curated vocabulary directly into a 41 MB ONNX (a YOLOE-26 export), and the YOLOv8-style head is decoded with a small hand-written NMS in detector.js. The "prompting" experience is a set of class chips: pick which vocabulary classes you care about and the detector filters to them — no server round-trip, no encoder.

Making detections trustworthy: tracking + gating

A raw per-frame detector is noisy — boxes flicker, the same object gets logged dozens of times. VisionLog adds a lightweight client-side tracker (tracker.js) that assigns stable Object IDs across frames, plus confirmation gating: an object has to be seen for at least three consecutive frames before it's written to the database, and a confidence slider (default 0.40) sets the floor. Each row stored carries the track ID, class, and confidence — so the logged data reflects objects, not flickers.

From engineering demo to ML project: fine-tuning and evaluation

Running pretrained weights is engineering, not modeling. To make VisionLog read as a mid-level ML project, I added two things.

A domain fine-tune

I fine-tuned YOLO26-n on a Construction-PPE dataset (hard hats, vests, etc.). Before fine-tuning the model scored mAP@50 ≈ 0.0003 on those classes (it had never seen them); after, ≈ 0.458. The resulting ONNX is selectable in the app as "YOLO26n-PPE" with its 11 PPE classes — a concrete before/after that shows the model actually learned a new domain.

"Ask the data": a safe multi-agent text-to-SQL system

Every detection lands in PostgreSQL, which raises an obvious question: can a non-technical visitor explore that data without writing SQL? VisionLog's "Ask the data" tab is a LangGraph multi-agent loop that turns a plain-English question into a query and answers it:

author  ->  guard  ->  execute  ->  answer
   ^_______________|  (self-correct on error)

The author drafts SQL, the guard enforces a read-only, SELECT-only policy (no writes ever reach the database), execute runs it, and answer turns the result into prose. If a query errors, the graph loops back and self-corrects. It runs on a fast Groq-hosted LLM and answered a real question against the live database in 2.6 seconds end to end.

Why this matters. It bridges the two things I build most — computer vision and agentic AI — in one product: a CV model produces structured data, and an auditable agent makes that data conversational, with a hard safety boundary.

Deployment: free, and harder than it looks

VisionLog is live on Vercel with a Neon serverless Postgres, GitHub-connected for auto-deploy. Getting a hybrid static-frontend + Python-API project onto Vercel's free tier took real fighting: the Python bundle blew past the 250 MB limit until I excluded the frontend from it; static assets 404'd until the root package.json mounted the build at the right path; and Neon's postgresql:// URL had to be rewritten to a driver Vercel actually ships. Those are the kinds of integration problems that don't show up in a tutorial but decide whether a thing is actually online.
