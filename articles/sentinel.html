Sentinel: procurement agents with evidence and an approval gate

September 2026·8 min read·Sentinel
Open live console ↗View code ↗

A facility manager needs to open a 30-bed memory-care wing in 60 days. There is a $480,000 equipment budget, a purchasing contract, and a set of room-specific requirements. A useful assistant has to turn that request into an equipment plan, explain the selections, check supporting evidence, and preserve a clear point where a person decides whether to order.

Sentinel is my implementation of that workflow. It combines a Python agent graph, a C# catalog and ordering service, TypeScript tools, and a React operator console. The interesting part is how those pieces constrain one another: language models can help interpret a request, but prices come from the catalog, compliance findings need evidence, and placing an order requires an authorized human.

Start with a workflow people can inspect

The core is a LangGraph state machine: Planner, Sourcing, Compliance, Budget, and Audit. Shared state carries the facility specification, room breakdown, equipment lines, findings, substitutions, budget report, and audit entries. Each node has a narrow responsibility, and the routing code makes the next step explicit.

Facility request
    |
 Planner -> Sourcing -> Compliance -> Budget -> Audit
                ^           |           |        |
                +-----------+-----------+        v
                   bounded re-source loops   AWAITING_APPROVAL
                                                 |
                                          Human review
                                                 |
                                          Catalog order

The graph is not a straight line. Compliance can request a replacement for a problematic item. Budget can propose less expensive alternatives and send the cart back through sourcing. Those alternatives are checked again before the graph finishes. The loop count is bounded so the system cannot spend indefinitely trying to satisfy an impossible request.

This distinction matters when a budget is infeasible. The report needs to preserve the shortfall. Quietly dropping required equipment to make the total look acceptable would produce a misleading plan.

Keep the catalog in charge of products and prices

The ASP.NET Core service owns catalog search, contract pricing, substitutions, stock lookup, and order creation. The agent talks to it through typed tool calls. It does not invent a product SKU or calculate a contract discount from a language-model response.

Sourcing turns the planner's room and category requirements into candidate equipment lines. Pricing is resolved through the catalog's contract endpoints. The resulting cart retains quantities, unit prices, contract identifiers, and list-price comparisons so the console can explain the spend.

The project uses a representative senior-care catalog and modeled pricing to exercise this integration. The architectural boundary is the important part: an existing purchasing system can remain the system of record while an agent coordinates the work around it.

Compliance needs a third answer: abstain

A binary pass/fail interface encourages certainty where the available evidence may not justify it. Sentinel uses three outcomes: PASS, VIOLATION, and ABSTAIN. Missing product attributes and missing regulatory support are reasons to request review, rather than reasons to invent a positive or negative finding.

The TypeScript MCP tool surface exposes reg_search, validate_item, validate_layout, and cost_calc. Inputs and outputs have Zod schemas; the Python graph uses Pydantic models, and the C# service uses DTOs. Those boundaries make malformed tool results visible before they silently contaminate the next stage.

Rules establish the first layer of evidence

Deterministic attribute rules reference entries in the project's regulation corpus. The corpus includes public physical-environment material and life-safety references relevant to the sample scenarios. When an explicit attribute violates a modeled rule, the finding carries its rule identifier and citation. If an attribute is absent, the tool treats the condition as not assessable.

Retrieved text constrains the language-model explanation

For retrieval-backed findings, the explanation has to clear a grounding gate: the retrieved passage must support the claim. Unsupported output becomes an abstention with a gate-blocked marker. The console displays the verdict, rationale, source reference, and supporting text together, so an operator can inspect the basis of a recommendation.

The central contract: a compliance assertion needs supporting evidence. An abstention is an actionable result: it tells the reviewer exactly where the system could not establish the answer.

A planted violation makes the behavior testable

One built-in scenario introduces a bedside-only call station into a memory-care equipment request. The item has an explicit attribute mismatch in the modeled scenario. The compliance stage flags it, attaches the relevant corpus reference, and can propose a replacement from the catalog.

That gives the demo a concrete engineering question: does the system catch the planted problem, cite the expected source, and retain the remaining plan? Other scenarios exercise egress-door attributes, bed safety, cleanability, flooring, and tight budgets. Clean carts are equally important: a system that marks everything as a violation can look cautious while creating unusable work for operators.

Approval is enforced beyond the interface

The Audit node finalizes the plan as AWAITING_APPROVAL. Operators can submit and inspect plans. Approvers and administrators can authorize order placement. That role distinction appears in the console, but it is also enforced by the API.

The C# ordering service independently checks the approver's JWT. The Python agent forwards the authorized token rather than using an unrestricted service identity to bypass the gate. Violating lines are excluded from the order request. This provides a second enforcement point at the system that actually creates the order.

Tenant identity travels with the authenticated user, plan runs, and audit records. Reads are tenant-scoped, with a separate cross-tenant administrator role. When PostgreSQL is configured, plans and append-only audit records survive process restarts. The offline development path has an in-memory fallback.

Evaluate the workflow, then monitor its cost

The repository's evaluation harness runs 12 golden scenarios. It measures planted-violation recall, citation accuracy, grounding, false violations, plan completeness, and feasible-budget adherence. An infeasible budget is a deliberate test case, not a result to hide.

The checked-in July 1, 2026 report passes those gates, including all planted violations caught and zero false violations on clean scenarios. These are results on a small, defined offline suite. They do not establish accuracy across every facility, product, or regulatory interpretation. The report's zero model spend and millisecond timings describe that offline evaluation path, not hosted LLM performance.

Runtime monitoring records node latency, model usage, token cost, and tool success. The system includes Prometheus metrics, readiness checks, structured logs, optional Langfuse export, and a per-request cost ceiling. Those details make it possible to investigate a slow or expensive request at the stage that caused it.

Model routing is a capability boundary

The provider layer separates structured planning, compliance reasoning, and grounding checks. Configured model providers can handle those capabilities, with fallback paths for unavailable services. The implementation deliberately retains deterministic planning when a free-model route cannot reliably preserve category coverage.

The hosted prototype currently supports a heuristic backend path, and the console has an explicitly labeled sample fallback when the backend is unavailable. The interface keeps those states visible. That distinction makes the prototype useful for exploring the workflow without confusing a recorded plan with a new live model response.

The console follows the reviewer

The React console brings the request, live agent trace, compliance findings, cart, and approval queue into one workspace. A slate-blue palette separates it from my other projects. On wide screens, navigation and monitoring flank the plan; tablets move monitoring below the main workflow; phones use collapsible facility details and horizontally scrollable tables.

I tested the populated layout across widths from 320 to 2560 pixels. The point was to keep the actual review tasks usable: reading a finding, checking a quantity, and locating the approval boundary, rather than merely making the login page fit.

What the project demonstrates

Sentinel brings agents into an existing operational architecture through explicit contracts. The graph coordinates; tools validate; the catalog owns ordering; evidence constrains claims; a person authorizes the final action. That separation makes the system easier to test, explain, and extend.

Further work would expand the reviewed corpus and evaluation set, exercise real supplier integrations, and measure hosted-model behavior under realistic workloads. The present build establishes the end-to-end interfaces and the failure paths those integrations need.
